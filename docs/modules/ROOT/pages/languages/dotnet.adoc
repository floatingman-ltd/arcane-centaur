== .NET Guide (C# and F#)

Full support for C# and F# including LSP, REPL-driven development, and
format-on-save. Both languages share the .NET SDK and the same iron.nvim
REPL keymaps.

[[quick-start]]
== Quick Start

=== C#

[arabic]
. Open any `.cs` file — Roslyn attaches automatically.
. If the project has multiple `.sln` files, run `:Roslyn target` to
pick the solution.
. Start the REPL with `,sl` on any line, or open it explicitly via
iron.nvim's `:IronRepl`.

=== F#

[arabic]
. Verify prerequisites:
+
[source,sh]
----
dotnet --version
dotnet tool list -g | grep fsautocomplete
----
. Open a `.fs` source file — plugins and LSP attach automatically.
. Start the REPL with `,sl` on any line.

[[csharp-lsp]]
== C# — LSP (Roslyn)

All standard LSP keybindings apply in `.cs` buffers:

[width="100%",cols="50%,50%",options="header",]
|===
|Keys |Action
|`gd` |Go to definition
|`K` |Hover documentation
|`gr` |Find references
|`++<++leader++>++rn` |Rename symbol
|`++<++leader++>++ca` |Code action (includes _Fix all_, _Nested actions_, _Complex edits_)
|`++<++leader++>++e` |Show diagnostic float
|`++[++d` / `++]++d` |Previous / next diagnostic
|===

Roslyn also supports:

* *Multiple solution files* — use `:Roslyn target` to switch between them.
* *Source-generated files* — navigates into generated code transparently.
* *Broad root detection* — set `broad++_++search = true` in the plugin opts if your `.sln` lives above the project root.

[[iron-commands]]
=== REPL Commands (C# and F#)

iron.nvim loads with the first `.cs` or F# buffer; its commands exist from then on.
`[ft]` defaults to the current buffer's filetype — `cs` (csharprepl) or `fsharp`
(`dotnet fsi`) — and `<Tab>` completes it.

[cols="1,2",options="header"]
|===
|Command |Action
|`:IronRepl [ft]` |Open the REPL in the bottom split; if it is already running, show
or hide its window
|`:IronReplHere [ft]` |Open the REPL in the current window instead of a split
|`:IronFocus [ft]` |Move the cursor into the REPL window, starting the REPL if needed
|`:IronHide [ft]` |Close the REPL window; the REPL keeps running
|`:IronRestart` |Start a fresh REPL of the same filetype and wipe the old one, without
asking
|`:IronSend \{text}` |Send `text` to the current filetype's REPL
|`:IronSend! \{ft} \{text}` |Send `text` to the `ft` REPL, starting it if needed
|`:IronWatch file` |On every write of this buffer, send the whole file
|`:IronWatch mark` |On every write of this buffer, resend the region last sent with
`,sl` / `,sc`
|`:IronAttach \{ft}` |Make this buffer send to the `ft` REPL whatever its own filetype,
e.g. `:IronAttach fsharp` in a scratch buffer
|===

There is no command to stop `:IronWatch`; `:lua require("iron.core").unwatch(0)` removes
the watch from the current buffer.

[[fsharp-indent]]
== F# — Indentation

Pressing Enter after a line that opens a body — one ending in `=`, `->`,
`then`, `else`, or a `match` arm — indents the new line one `shiftwidth`
deeper. `==`, `>>` and `<<` work as reindent operators.

*This comes from the editor, not from the language server.* No language
server supplies indentation; LSP has no indent-as-you-type concept.
Indentation therefore keeps working with `fsautocomplete` absent, still
starting, or unable to resolve options for a standalone `.fsx`.

[NOTE]
====
The implementation is a *vendored* third-party file, `indent/fsharp.vim`,
taken from https://github.com/ionide/Ionide-vim[Ionide-vim] at a recorded
commit. The plugin itself is deliberately **not** installed: only that one
file is wanted, and the rest of the plugin duplicates configuration that
already works here — it registers a second FsAutoComplete client, sets
`fdm=syntax` in place of the LSP folds, ships a regex syntax file instead
of treesitter, changes `commentstring`, and binds FSI keymaps that collide
with iron.nvim.

One function in the vendored file differs from upstream: its comment and
string detection used `synID()`, which needs a Vim `:syntax` file and so
was inert under treesitter highlighting. Read the file's header before
editing or refreshing it.
====

Commenting is fixed in the same place and for the same reason. Neovim ships no
`ftplugin` for F#, so `commentstring` was unset and `++<++leader++>++`-style
native commenting (`gcc`, `gc`) failed with *comment string is empty*. F# buffers
now use `++/++++/++ %s`, with `comments` set so XML doc comments (`++/++++/++++/++`)
are recognised ahead of plain line comments and `(* *)` blocks are handled.

F# is the only language here that needs a hand-written indent script.
nvim-treesitter ships no `indents.scm` for F#, and `smartindent` keys off
`{`, `}` and `cinwords`, none of which F# uses.

[[fsharp-formatting]]
== F# — Formatting (fsautocomplete)

Format-on-save is enabled via `conform.nvim` using the fsautocomplete formatter, which in turn
delegates to https://fsprojects.github.io/fantomas/[Fantomas].

[IMPORTANT]
====
*Fantomas must be installed separately* — `dotnet tool install -g fantomas`. fsautocomplete does
not ship it, and without it a write does not merely skip formatting: the server raises an
interactive prompt

[source]
----
No Fantomas install was found.:
1: Install locally
2: Install globally
----

which blocks every save of an F# buffer.
====

[WARNING]
====
*Format-on-save needs resolved project options, so it is unreliable on a
standalone `.fsx` script.* fsautocomplete resolves options per project; for a
script outside any `.fsproj` that resolution intermittently cancels with

[source]
----
Error getting project options for <path> - A task was canceled.
----

after which Fantomas is never invoked and the buffer writes *unformatted* with
nothing else in `++:++messages` to explain it. It is a race, so the same file may
format one time and not the next.

Inside a project it is reliable. If a script must be formatted, `++<++leader++>++f`
after the server has settled is more dependable than relying on the write.
====

Fantomas applies its own house style, not just indentation repair — it will collapse multi-line
`match` arms and `if`/`elif`/`else` chains onto single lines where they fit, and normalise
`Rect (w, h)` to `Rect(w, h)`. Expect saved files to be restructured, not merely re-indented.

Manual trigger:

[cols=",",options="header",]
|===
|Keys |Action
|`++<++leader++>++f` |Format buffer or visual selection
|===

[[debugging]]
== Debugging (nvim-dap + netcoredbg)

Breakpoint debugging for C# and F# is provided by https://github.com/mfussenegger/nvim-dap[nvim-dap] +
https://github.com/rcarriga/nvim-dap-ui[nvim-dap-ui] with the https://github.com/Samsung/netcoredbg[netcoredbg]
adapter, which easy-dotnet auto-registers with nvim-dap once both are loaded (there is no
hand-written `dap.adapters` entry — a session therefore only starts from a `.cs`/`.fsharp` buffer,
where easy-dotnet is loaded).

=== Prerequisites

`netcoredbg` is *not* a NuGet / `dotnet tool` package (there is no `dotnet tool install -g netcoredbg`).
Download the prebuilt binary from the
https://github.com/Samsung/netcoredbg/releases[Samsung/netcoredbg releases] and put it on your `$PATH`.

*Linux / WSL2 (x64):*

[source,sh]
----
# Resolve the latest release tag, download the linux-amd64 build, and extract it
NCDBG_VER=$(curl -s https://api.github.com/repos/Samsung/netcoredbg/releases/latest \
  | grep '"tag_name"' | cut -d'"' -f4)
curl -L "https://github.com/Samsung/netcoredbg/releases/download/${NCDBG_VER}/netcoredbg-linux-amd64.tar.gz" \
  -o /tmp/netcoredbg.tar.gz
mkdir -p ~/.local/share/netcoredbg
tar -xzf /tmp/netcoredbg.tar.gz -C ~/.local/share/netcoredbg/

# Locate the binary — the archive unpacks into a nested netcoredbg/ directory
find ~/.local/share/netcoredbg -name netcoredbg -type f

# Add that directory to PATH (~/.zshenv), then reload
echo 'export PATH="$HOME/.local/share/netcoredbg/netcoredbg:$PATH"' >> ~/.zshenv
exec zsh
----

Verify it is on your `$PATH`:

[source,sh]
----
netcoredbg --version
----

[NOTE]
====
Release 3.2.0-1092 unpacks to `~/.local/share/netcoredbg/netcoredbg/netcoredbg`. If `find` prints a
different directory for a later release, put that directory on `PATH` instead.
====

=== Debug Keymaps

[cols=",,",options="header",]
|===
|Keys |Mode |Action
|`<F9>` or `++<++leader++>++bb` |Normal |Toggle breakpoint
|`<F5>` or `++<++leader++>++bc` |Normal |Start or continue the debug session
|`<F10>` or `++<++leader++>++bv` |Normal |Step over
|`<F11>` or `++<++leader++>++bi` |Normal |Step into
|`<F12>` or `++<++leader++>++bo` |Normal |Step out
|`<S-F5>` or `++<++leader++>++bt` |Normal |Terminate debug session
|`++<++leader++>++bu` |Normal |Toggle debug UI
|`++<++leader++>++br` |Normal |Open debug REPL
|===

[NOTE]
====
Every action has both a function-key and a `++<++leader++>++b` binding. The F-keys are the
universal debugger idiom and work on server/SSH terminals; the `++<++leader++>++b` mirrors are for
GUI terminal emulators that intercept function keys before Neovim sees them (commonly `<F11>` for
fullscreen, `<F10>` for a menu). Both are always active — use whichever your terminal passes through.
====

The debug UI opens automatically when a session starts and closes on exit.
Launch configurations are auto-discovered by easy-dotnet from the project structure
(no hand-authored `launch.json` required).

[[dap-commands]]
=== Debug Commands

nvim-dap loads on the first debug key press, or when a `.cs`/`.fs` buffer loads
easy-dotnet (which requires nvim-dap to register netcoredbg). The `:Dap*` commands exist
from then on. The same commands work in Haskell buffers.

[cols="1,2",options="header"]
|===
|Command |Action
|`:DapContinue` |Start a session, or resume a paused one; same as `<F5>` or
`++<++leader++>++bc`
|`:DapNew [name...]` |Start a new session even if one is running; with names, start
each launch configuration of that name
|`:DapToggleBreakpoint` |Set or remove a breakpoint on the current line; same as `<F9>` or
`++<++leader++>++bb`
|`:DapClearBreakpoints` |Remove every breakpoint
|`:DapStepOver` |Step over; same as `<F10>` or `++<++leader++>++bv`
|`:DapStepInto` |Step into; same as `<F11>` or `++<++leader++>++bi`
|`:DapStepOut` |Step out; same as `<F12>` or `++<++leader++>++bo`
|`:DapPause` |Pause the current thread, or pick a thread to pause
|`:DapRestartFrame` |Restart the current stack frame (if the adapter supports it)
|`:DapTerminate` |End the session and the debuggee; same as `<S-F5>` or
`++<++leader++>++bt`
|`:DapDisconnect` |Detach from the session and leave the debuggee running
|`:DapToggleRepl` |Open or close the nvim-dap REPL in its own split.
`++<++leader++>++br` only opens it
|`:DapEval` |Open a `dap-eval://` scratch split; type expressions and `:w` to evaluate.
With a range (`:'++<++,'>DapEval`) the selected lines are copied in; `:DapEval!`
evaluates at once
|`:DapSetLogLevel \{level}` |Set the nvim-dap log level (`TRACE`, `DEBUG`, `INFO`,
`WARN`, `ERROR`)
|`:DapShowLog` |Open the nvim-dap log in a split
|===

`++<++leader++>++bu` (toggle debug UI) has no `:Dap` equivalent; it calls nvim-dap-ui.

== Testing (easy-dotnet)

https://github.com/GustavEikaas/easy-dotnet.nvim[easy-dotnet.nvim] provides a
.NET test runner, project picker, and solution management using fzf-lua. It does
NOT manage the Roslyn LSP — roslyn.nvim remains the sole C# language server.

[IMPORTANT]
====
easy-dotnet.nvim is a thin client over a separate **`EasyDotnet` server tool**, which powers *all*
its features (debug, test, run, build). Install it once:

[source,sh]
----
dotnet tool install -g EasyDotnet     # provides the `dotnet-easydotnet` executable
dotnet-easydotnet -v                  # verify (needs ~/.dotnet/tools on PATH)
----

Without it, every `:Dotnet …` action (and `<F5>` debug) errors
`'dotnet-easydotnet' is not executable`. Run `:checkhealth easy-dotnet` to confirm the server and
the other dependencies (dap, fzf-lua, the `c_sharp` parser).
====

=== Test / Run / Build Keymaps (C# and F# buffers)

[cols=",",options="header",]
|===
|Keys |Action
|`,tt` |Run tests for selected project
|`,tr` |Run selected project
|`,tb` |Build selected project
|===

Run/test output opens in a managed terminal that **stays open on exit** (we set
`managed_terminal.auto_hide = false`; the default closes it the moment a run exits 0). Dismiss it
with `q`.

[NOTE]
====
easy-dotnet resolves the target project from Neovim's **current working directory**
(`vim.fn.getcwd()`), not the current buffer, and it caches one active project (shown in lualine).
Open Neovim **from the project's directory** (or `:lcd %:p:h`) so `,tr`/`,tt`/`,tb` act on the
project you mean.

**F# projects need a solution file.** easy-dotnet's runnable-project discovery is C#-oriented, so a
standalone `.fsproj` isn't found ("No runnable projects found") even though `dotnet run` works — add
a `.sln` (or `.slnx`) alongside it. C# `.csproj` projects are discovered without one.
====

=== Easy-Dotnet Commands

Every easy-dotnet action is a `:Dotnet` subcommand; `:Dotnet <Tab>` completes them. They are
available once a `.cs` or `.fs` buffer has loaded the plugin.

*Picking a project.* The plain form of a command opens a picker every time. The `default` form
asks once, remembers the choice, and reuses it; `:Dotnet reset` forgets it.

*Arguments.* `run`, `debug`, `watch`, `build`, `test` and `restore` accept trailing arguments.
`release` or `debug` as the first argument is shorthand for `-c Release` / `-c Debug`, e.g.
`:Dotnet build release`. For `build`, `test` and `restore` the rest go to the `dotnet` command
line; for `run`, `debug` and `watch` they are passed through to the run.

== Typical Workflow

....
 +------------------------------------------------------+
 |  Neovim                                              |
 |  +--------------------------+---------------------+  |
 |  |  Program.cs / hello.fs   |  REPL               |  |
 |  |                          |                     |  |
 |  |  var x = 42;             |  > var x = 42;      |  |
 |  |  Console.WriteLine(x);   |  42                 |  |
 |  |                          |                     |  |
 |  |  ,sl to send line -------+                     |  |
 |  +--------------------------+---------------------+  |
 +------------------------------------------------------+
....

[arabic]
. Open a `.cs` or `.fs` file — LSP starts and diagnostics appear.
. Send snippets to the REPL with `,sl` / `,sc` to explore APIs interactively.
. `++<++leader++>++f` (or save) formats with CSharpier / fsautocomplete.
. Use `gd` / `gr` / `++<++leader++>++ca` for full IDE-style navigation and refactoring.

== Troubleshooting

=== Roslyn does not attach

Check that `Microsoft.CodeAnalysis.LanguageServer` is on your `$PATH`:

[source,sh]
----
which Microsoft.CodeAnalysis.LanguageServer
----

If not found, re-run the install steps in xref:#setup[Setup].

=== fsautocomplete does not attach

Check that it's installed:

[source,sh]
----
dotnet tool list -g | grep fsautocomplete
----

Run `:lua =vim.lsp.get_clients({bufnr=0})` inside Neovim to check whether
the server is attached to the current buffer. To open the LSP log:

[source,vim]
----
:lua vim.cmd('e ' .. vim.lsp.get_log_path())
----

`:checkhealth lsp` gives a broader overview of LSP status.

=== REPL does not open

Check that the REPL backend binary is on your `$PATH`:

[source,sh]
----
which csharprepl      # C#
dotnet fsi --version  # F#
----

=== Installing .NET Global Tools

dotnet tool install -g csharpier    # C# formatter
dotnet tool install -g csharprepl   # C# interactive REPL
dotnet tool install -g fsautocomplete  # F# language server
dotnet tool install -g fantomas     # F# formatter (fsautocomplete delegates to it)
dotnet tool install -g EasyDotnet   # server tool for easy-dotnet.nvim
----

To install whichever are missing and update the rest in one go:

[source,sh]
----
for t in csharpier csharprepl fsautocomplete fantomas EasyDotnet; do dotnet tool install -g $t || dotnet tool update -g $t; done
dotnet tool list -g
----

The commands land in `~/.dotnet/tools`, which must be on `$PATH` — see <<dotnet-sdk,Installing .NET SDK>>.

=== Installing the Roslyn Language Server

The Roslyn LSP is the official Microsoft C# language server used in
VS Code's C# Dev Kit. It is *not* installed via `dotnet tool install`,
and it is *not* on the public nuget.org feed. It is published to
Microsoft's Azure DevOps *vs-impl* feed, and every release is a
prerelease (there is no stable `5.x` — the newest is `5.4.0-2.26179.14`
at the time of writing; there is no `5.5`/`5.6`).

*Linux / WSL2 (x64):*

[source,sh]
----
# 1. Resolve the newest version from the Azure DevOps vs-impl feed
PKG=microsoft.codeanalysis.languageserver.linux-x64
FEED="https://pkgs.dev.azure.com/azure-public/vside/_packaging/vs-impl/nuget/v3/flat2/${PKG}"
VERSION=$(curl -s "${FEED}/index.json" | tr ',' '\n' | grep -oE '[0-9][0-9.]+-[0-9.]+' | sort -V | tail -1)
echo "Installing Roslyn LSP ${VERSION}"

# 2. Download the linux-x64 package (self-contained native binary)
mkdir -p ~/.local/share/roslyn
curl -L "${FEED}/${VERSION}/${PKG}.${VERSION}.nupkg" -o /tmp/roslyn.nupkg

# 3. Extract into the install directory and make executable (needs `unzip`)
unzip -o -q /tmp/roslyn.nupkg -d ~/.local/share/roslyn
chmod +x ~/.local/share/roslyn/content/LanguageServer/linux-x64/Microsoft.CodeAnalysis.LanguageServer

# 4. Add to PATH (~/.zshenv — see Installing .NET SDK for why), then reload
echo 'export PATH="$HOME/.local/share/roslyn/content/LanguageServer/linux-x64:$PATH"' >> ~/.zshenv
exec zsh

# 5. Verify
Microsoft.CodeAnalysis.LanguageServer --version
----

[TIP]
====
Browse all versions at `${FEED}/index.json`. The `nuget.org` package of
the same name carries only a single stale prerelease — do not use it.
To pin a specific version instead of auto-resolving the newest, set
`VERSION=` manually (e.g. `VERSION=5.4.0-2.26179.14`).
====

[[dotnet-sdk]]
=== Installing .NET SDK

Install every SDK you need — here .NET 8 and .NET 10 — side by side into `~/.dotnet` with
Microsoft's `dotnet-install.sh`. One `dotnet` then serves both: it builds with the newest SDK
unless a repo's `global.json` pins an older one, and runs each project on the runtime matching its
`<TargetFramework>`.

*Linux / WSL2 (Ubuntu):*

[source,sh]
----
curl -sSL https://dot.net/v1/dotnet-install.sh -o /tmp/dotnet-install.sh
bash /tmp/dotnet-install.sh --channel 10.0 --install-dir ~/.dotnet
bash /tmp/dotnet-install.sh --channel 8.0 --install-dir ~/.dotnet
----

Re-running either `--channel` line later installs the latest patch next to the existing one.

Then put the install on `$PATH`, together with `~/.dotnet/tools` where `dotnet tool install -g`
puts its commands. Under zsh, use `~/.zshenv`: zsh reads it for every shell, including ones that
do not descend from your interactive terminal (an `ssh host cmd`, `wsl.exe -e`, a scheduled job),
whereas `~/.zshrc` is read only by interactive shells. `typeset -U` drops duplicate `$PATH`
entries when shells nest.

[source,sh]
----
printf '%s\n' 'typeset -U path PATH' 'export DOTNET_ROOT="$HOME/.dotnet"' 'export PATH="$HOME/.dotnet:$HOME/.dotnet/tools:$PATH"' >> ~/.zshenv
exec zsh
----

Verify, from a fresh non-interactive shell:

[source,sh]
----
zsh -c 'echo $DOTNET_ROOT; command -v dotnet'   # ~/.dotnet and ~/.dotnet/dotnet
dotnet --list-sdks                              # an 8.0.x and a 10.0.x line
dotnet --list-runtimes                          # Microsoft.NETCore.App 8.0.x and 10.0.x
----

[WARNING]
====
*Do not mix this with Ubuntu's apt packages.* apt (`dotnet-sdk-8.0` and friends) installs to
`/usr/lib/dotnet` and carries one version per package source, so it cannot supply 8 and 10 together
on Ubuntu 24.04. It also writes `/etc/dotnet/install_location`, which points at `/usr/lib/dotnet`;
a global tool started without `DOTNET_ROOT` set looks there, finds no .NET 10 runtime, and fails
even though `dotnet --list-runtimes` in your shell lists one. Check for a leftover apt install:

[source,sh]
----
dpkg -l | grep -i dotnet                                   # should print nothing
which -a dotnet; cat /etc/dotnet/install_location* 2>/dev/null
----

If `dpkg` lists packages, remove them (read apt's removal list before confirming):

[source,sh]
----
sudo apt remove dotnet-sdk-8.0 dotnet-runtime-8.0 dotnet-host-8.0 dotnet-hostfxr-8.0 dotnet-apphost-pack-8.0 dotnet-targeting-pack-8.0 dotnet-templates-8.0
----

If you keep them, `DOTNET_ROOT` and the `~/.dotnet` entry ahead of `/usr/bin` on `$PATH` are what
keep the apt copy out of the way.
====

[NOTE]
====
Running or debugging a project needs the **runtime that matches its `<TargetFramework>`**, not
just any SDK. The 10.0 SDK builds a `net8.0` project, but running it needs
`Microsoft.NETCore.App 8.0.x`, which the `--channel 8.0` install provides. Microsoft's support for
.NET 8 ended on 2026-11-10; .NET 10 is the current LTS. The editor toolchain here (roslyn.nvim,
fsautocomplete, csharprepl, easy-dotnet, netcoredbg) works with either.
====

=== Verifying the toolchain

Once the SDKs, global tools, Roslyn, and netcoredbg are installed, build and run one project per
target framework:

[source,sh]
----
dotnet new console -f net8.0 -o /tmp/t8 && dotnet run --project /tmp/t8      # Hello, World!
dotnet new console -f net10.0 -o /tmp/t10 && dotnet run --project /tmp/t10   # Hello, World!
dotnet new console -lang F# -o /tmp/f10
----

Then, in Neovim:

[arabic]
. `cd /tmp/t10 && nvim Program.cs`, wait for the project to load, and run `:checkhealth vim.lsp` — it lists an active `roslyn` client.
. `K` on `Console` opens hover documentation.
. Indent the `Console.WriteLine` line wrongly and `:w` — CSharpier restores it.
. `<F9>` on that line, then `<F5>` — the debugger stops there and dap-ui opens. `<S-F5>` ends the session.
. `cd /tmp/f10 && nvim Program.fs` — `:checkhealth vim.lsp` lists `fsautocomplete`, and `:w` saves without a "No Fantomas install was found" prompt.

Clean up with `rm -rf /tmp/t8 /tmp/t10 /tmp/f10`.
