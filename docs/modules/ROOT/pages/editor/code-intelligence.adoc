== LSP

These keymaps are active in any buffer where an LSP server has attached
(F#, C#, Markdown, Haskell, Janet, Lua).

[cols=",,",options="header",]
|===
|Keys |Mode |Action
|`gd` |Normal |Go to definition
|`K` |Normal |Hover documentation
|`gr` |Normal |Find all references
|`++<++leader++>++rn` |Normal |Rename symbol
|`++<++leader++>++ca` |Normal |Code action
|`++<++leader++>++e` |Normal |Show diagnostic float
|`++[++d` |Normal |Jump to previous diagnostic
|`++]++d` |Normal |Jump to next diagnostic
|===

=== Configured LSP Servers

[width="100%",cols="34%,33%,33%",options="header",]
|===
|Server |Language |Install
|`fsautocomplete` |F# |`dotnet tool install -g fsautocomplete` (plus `dotnet tool install -g fantomas` for formatting)
|`roslyn` |C# |See xref:languages/dotnet.adoc[.NET guide]
|`marksman` |Markdown |https://github.com/artempyanykh/marksman/releases[GitHub release binary] → `~/.local/bin`
|`janet_lsp` |Janet |`jpm install janet-lsp`
|`haskell-language-server` |Haskell |`ghcup install hls` (managed by haskell-tools.nvim)
|`lua_ls` |Lua |See xref:languages/lua.adoc[Lua guide]
|===

_Keymaps defined in `lua/config/lsp.lua`._

[NOTE]
====
`marksman` supplies hover, go-to-definition, references, rename, document symbols, code actions and completion — but *not* folding ranges or formatting. Markdown folds come from treesitter with an indent fallback (see xref:editor/navigation.adoc[Navigation]), and no LSP-backed markdown formatter is configured.

`fsautocomplete` supplies all of the above *plus* folding ranges, signature help and formatting, so F# gains LSP folds and format-on-save. It does not supply indentation — no language server does, since LSP has no indent-as-you-type concept. F# indentation comes from the editor instead, via a vendored `indent/fsharp.vim`, and therefore keeps working with no server attached. See xref:languages/dotnet.adoc#fsharp-indent[F# — Indentation].

Formatting needs a *second* binary: fsautocomplete delegates it to https://fsprojects.github.io/fantomas/[Fantomas] and does not ship it. Without `fantomas` on `$PATH` the write does not silently skip formatting — the server raises an interactive `No Fantomas install was found.` prompt that blocks every save of an F# buffer. Install it with `dotnet tool install -g fantomas`.

fsautocomplete also cannot answer for a bare `.fs` file that sits outside any project: such a file is never added to its loaded projects, so requests fail with `Couldn't find <path> in LoadedProjects` and opening one is enough to log an `UnhandledPromiseRejection`. Work inside a project, or use a `.fsx` script, which it resolves on its own.
====

== Diagnostics Panel (trouble.nvim)

https://github.com/folke/trouble.nvim[trouble.nvim] v3 provides a structured
panel for diagnostics, references, quickfix, and todos.

[cols=",,",options="header",]
|===
|Keys |Mode |Action
|`++<++leader++>++xx` |Normal |Project diagnostics panel
|`++<++leader++>++xX` |Normal |Buffer diagnostics panel
|`++<++leader++>++xs` |Normal |Symbols panel
|`++<++leader++>++xr` |Normal |LSP references / definitions panel
|`++<++leader++>++xl` |Normal |Location list panel
|`++<++leader++>++xq` |Normal |Quickfix list panel
|`++<++leader++>++xt` |Normal |Todo list (via Trouble)
|`++<++leader++>++xT` |Normal |Todo list (via fzf-lua)
|===

=== Using the panel

Every `++<++leader++>++x*` map is a *toggle*: press it once to open the panel,
again to close it. Inside the panel, `j`/`k` move between entries, `Enter` jumps
to the location under the cursor (the panel stays open), `q` closes the panel,
and `?` lists every in-panel keybinding (preview, fold, filter, delete, …).

Pick the source for the job:

[cols=",",options="header",]
|===
|Panel |What it shows
|Project diagnostics (`++<++leader++>++xx`) |Every LSP warning/error across the whole workspace
|Buffer diagnostics (`++<++leader++>++xX`) |Diagnostics for the current file only
|Symbols (`++<++leader++>++xs`) |Outline of the current file (functions, classes, …); opens to the side and leaves the cursor in your code
|LSP refs/defs (`++<++leader++>++xr`) |References and definitions of the symbol under the cursor, in a right-hand panel
|Location list (`++<++leader++>++xl`) |The current window's location list
|Quickfix (`++<++leader++>++xq`) |The quickfix list — fill it first with `gr`, `:grep`, `:make`, or `:lua vim.diagnostic.setqflist()`
|===

=== The `:Trouble` command

Every `++<++leader++>++x*` map is a call to `:Trouble`, which takes a mode,
an action and options in that order:

[source,vim]
----
:Trouble [mode] [action] [options]
----

`:Trouble` with no arguments opens a picker listing every mode. The action
defaults to `open`; the maps use `toggle`. `close` and `refresh` are also
accepted. `Tab` completes modes, actions and option names.

[cols=",,",options="header",]
|===
|Mode |Shows |Map
|`diagnostics` |LSP diagnostics for the workspace |`++<++leader++>++xx`
|`symbols` |Document symbols of the current buffer |`++<++leader++>++xs`
|`lsp` |Definitions, references, implementations, type definitions, declarations and incoming/outgoing calls of the symbol under the cursor |`++<++leader++>++xr`
|`lsp_references`, `lsp_definitions`, `lsp_implementations`, … |One of the sections of `lsp` on its own |—
|`qflist` (alias `quickfix`) |The quickfix list |`++<++leader++>++xq`
|`loclist` |The current window's location list |`++<++leader++>++xl`
|`todo` |Todo comments across the project (registered by todo-comments.nvim) |`++<++leader++>++xt`
|===

Options are `key=value` pairs, dotted for nested keys. Values may be Lua
expressions:

[cols=",",options="header",]
|===
|Command |Effect
|`:Trouble diagnostics toggle filter.buf=0` |Diagnostics for the current buffer only — `buf=0` means the current buffer (`++<++leader++>++xX`)
|`:Trouble symbols toggle focus=false` |Open the panel but leave the cursor in the code window (`++<++leader++>++xs`)
|`:Trouble lsp toggle win.position=right` |Put the panel on the right instead of the bottom (`++<++leader++>++xr`)
|`:Trouble diagnostics filter.severity=vim.diagnostic.severity.ERROR` |Errors only
|===

The `telescope`, `snacks` and `fzf` modes also appear in the completion
list. They show results sent from those pickers, and nothing here sends
any, so they open empty. Telescope and snacks.nvim are not installed.

=== Todo comments (todo-comments.nvim)

https://github.com/folke/todo-comments.nvim[todo-comments.nvim] highlights
annotation keywords in your comments — coloured text plus a sign in the gutter —
and can list them across the whole project. A keyword is only recognised when
written with a trailing colon (`TODO:`) inside a comment.

[cols=",",options="header",]
|===
|Keyword |Aliases (same colour)
|`TODO:` |—
|`FIX:` |`FIXME:` `BUG:` `FIXIT:` `ISSUE:`
|`HACK:` |—
|`WARN:` |`WARNING:` `XXX:`
|`PERF:` |`OPTIM:` `PERFORMANCE:` `OPTIMIZE:`
|`NOTE:` |`INFO:`
|`TEST:` |`TESTING:` `PASSED:` `FAILED:`
|===

Two list views scan the whole project for these markers:

* `++<++leader++>++xt` (`:TodoTrouble`) — todos in a Trouble panel, navigated exactly like the panels above.
* `++<++leader++>++xT` (`:TodoFzfLua`) — todos in an fzf-lua fuzzy picker; type to filter, `Enter` to jump.

Two more commands put the same results into Vim's own lists, with no keymap:

[cols=",",options="header",]
|===
|Command |Action
|`:TodoQuickFix` |Fill the quickfix list with every todo and open it (`:copen`)
|`:TodoLocList` |Fill the current window's location list and open it (`:lopen`)
|===

Both accept two arguments:

* `cwd=++<++dir++>++` — search that directory instead of the working directory, e.g. `:TodoQuickFix cwd=~/projects/foo`.
* `keywords=++<++list++>++` — comma-separated, case-sensitive, no spaces, e.g. `:TodoLocList keywords=TODO,FIX`. Aliases are matched literally: `keywords=FIX` does not find `FIXME:`, so list each alias you want.

`:TodoQuickFix` output can then be opened in Trouble with `++<++leader++>++xq`.

NOTE: All four search with *ripgrep*, so `rg` must be on your `PATH`; the
fzf-lua view additionally needs the *fzf* binary. If either is missing the
command reports it (`rg was not found` / `'fzf' not installed`) rather than listing todos.

[[todo-telescope]]
`:TodoTelescope` also appears in `:Todo++<++Tab++>++` completion but does not work here: todo-comments
defines it unconditionally as `:Telescope todo-comments todo`, and Telescope is not installed, so it
fails with `E492: Not an editor command: Telescope todo-comments todo`. It never worked in this
config — Telescope was replaced by fzf-lua in 2025 and deleted on 2026-03-10, and todo-comments,
added on 2026-07-01, was set up around `:TodoFzfLua` and `:TodoTrouble`. Use `++<++leader++>++xT`
instead.

NOTE: `[d`/`]d` and `<leader>e` (LSP diagnostics float) are unchanged.
`]t`/`[t` are tag navigation, covered in <<tag-navigation>> below.

_Configured in `lua/plugins/trouble.lua` and `lua/plugins/todo-comments.lua`._

[[tag-navigation]]
== Tag Navigation (ctags)

A `tags` file is an index — generated by
https://github.com/universal-ctags/ctags[universal-ctags] — that maps every
symbol name to the file and line where it is defined. It gives cross-file
"jump to definition" in *any* language with no language server involved, and it
is what makes the `]t`/`[t` maps do anything.

Generate the index at the project root (Neovim finds `./tags` automatically).
The index is a static snapshot, so re-run this after significant edits:

[source,sh]
----
ctags -R          # writes ./tags (gitignored)
----

universal-ctags is a soft dependency — see
xref:getting-started.adoc#system-deps[System Dependencies] to install it.

[cols=",",options="header",]
|===
|Keys |Action
|`Ctrl-]` |Jump to the definition of the tag under the cursor
|`g Ctrl-]` |Same, but list the matches to choose from when there are several (`:tjump`)
|`Ctrl-o` |Jump back to where you came from (the jump list)
|`++]++t` / `++[++t` |Next / previous *match* when a tag has several definitions (vim-unimpaired → `:tnext` / `:tprevious`)
|`++]++T` / `++[++T` |Last / first match (`:tlast` / `:tfirst`)
|`:tag {name}` |Jump to a named tag; `:tag /pat` jumps to the first tag matching a pattern
|`:tselect {name}` |List all matching tags and pick one
|===

NOTE: `]t`/`[t` only move when the current tag has *more than one* definition —
with a single match there is nothing to cycle to (you may see `E428`/`E425` at
the list ends, which is normal). In LSP buffers, `gd` (go to definition) is
usually the better tool and needs no `tags` file.

CAUTION: Vim's built-in `Ctrl-t` (pop the tag stack) is remapped in this
configuration to toggle the file tree (`:NvimTreeToggle`). To step back after a
tag jump use `Ctrl-o` or `:pop` instead.

_`]t`/`[t`/`]T`/`[T` come from `tpope/vim-unimpaired`; `Ctrl-]`, `g Ctrl-]`, and `Ctrl-o` are Vim built-ins._

== Auto-Completion (blink.cmp)

Powered by https://github.com/saghen/blink.cmp[blink.cmp] v1 — a Rust-based
fuzzy completion engine with sub-millisecond latency. Replaces nvim-cmp.

=== Completion Menu

IMPORTANT: `Enter` does **not** accept a completion. Accept with `Ctrl-y`. `Enter`
always inserts a newline in insert mode and executes the command on the command line,
whether or not the menu is open and whether or not an entry is highlighted. If you are
used to `Enter` confirming a suggestion, this is the one key you have to relearn.

There is a single completion keymap, and it behaves identically in insert mode and on
the command line. Previously the two were configured separately and disagreed about
which key accepted.

[cols=",,",options="header",]
|===
|Keys |Mode |Action
|`Ctrl-n` |Insert, Command-line |Open the completion menu when it is closed; select the next suggestion when it is already open
|`Ctrl-p` |Insert, Command-line |Select previous suggestion
|`Ctrl-y` |Insert, Command-line |Accept the highlighted suggestion, or the top one if none is highlighted
|`Ctrl-e` |Insert, Command-line |Cancel — dismiss the menu and restore the text you typed
|`Ctrl-k` |Insert, Command-line |Show the documentation window for the selected entry
|`Ctrl-f` |Insert, Command-line |Scroll documentation preview down
|`Ctrl-b` |Insert, Command-line |Scroll documentation preview up
|===

==== The trigger key

`Ctrl-n` does double duty: it is the manual trigger *and* the select-next key. With the
menu closed it opens it; with the menu already open it walks down the list.

In practice the menu is usually already open, because it auto-shows the moment you type a
keyword (`show_on_keyword`). So while typing a word, the *first* `Ctrl-n` selects the first
entry. You only see the trigger role when the menu is genuinely closed — after dismissing
it with `Ctrl-e`, or when the cursor is not in a keyword at all.

Either way nothing is highlighted when the menu appears (`preselect = false`), so a
completion is never committed implicitly. Only an explicit `Ctrl-y` inserts anything.

This mirrors what insert-mode `Ctrl-n` already means in stock Vim.

NOTE: There is no `Alt-Space` trigger, despite what older revisions of these docs said.
This configuration runs under WSL in a Windows console, which claims `Alt-Space` for its
own system menu, so the keystroke never reached Neovim. `Ctrl-Space` is swallowed the
same way. Any manual trigger here has to be a plain `Ctrl`-plus-letter chord.

==== The documentation window

Selecting an entry shows a documentation window beside the menu after a short delay
(500ms). `Ctrl-f` and `Ctrl-b` scroll it, four lines at a time.

Two things make this less visible than you might expect. The window is 20 rows tall, and
the scroll keys clamp to the content, so a docstring that already fits will not appear to
move at all — the keys are working, there is simply nothing to scroll. And the window only
renders what the language server actually sends: an entry with neither `detail` nor
`documentation` closes it silently.

CAUTION: `lua_ls` supplies neither field on its completion entries, so **the documentation
window never appears in Lua buffers**, whatever you press. C# via roslyn is the reliable
place to see it. Since this configuration is mostly Lua, expect the window less often than
these keys suggest.

If the automatic window gets in the way, turn it off for the session:

[source,vim]
----
:BlinkDocsToggle
----

That switches between *timed* (the window appears on its own) and *on-demand* (it appears
only when you press `Ctrl-k`), reporting the new state. It is not persisted — every session
starts timed. `Ctrl-k` works in both modes, and needs an entry already selected, so it is
`Ctrl-n` then `Ctrl-k`. A window that is already open when you switch to on-demand keeps
following your selection until the menu closes.

TIP: `Ctrl-n` in *normal* mode is unrelated — it opens the file tree. The completion
keymap only binds insert and command-line modes.

[[spelling]]
=== Spelling suggestions

Spelling is on everywhere (`spell`, `spelllang=en_ca` in `lua/options.lua`), and
`++[++os` / `++]++os` / `yos` toggle it per window.

*Corrections do not come from the completion menu.* The `spell` completion source
offers dictionary words that *extend* what you have typed, which is a different
thing: a correction is by definition not a fuzzy match of the misspelling it
corrects, so blink's matcher discards it. Typing `recieve` and pressing `Ctrl-n`
therefore shows nothing. This is a deliberate trade-off, recorded in
`recommendations/ideas.md` — the alternative disables suggestion filtering
entirely and offers the full dictionary for every word of three or more
characters.

Use one of the two native routes instead:

[cols=",,",options="header",]
|===
|Keys |Mode |Action
|`Ctrl-x s` |Insert |Open a suggestion popup for the word before the cursor. Navigate with `Ctrl-n` / `Ctrl-p`, accept with `Ctrl-y`, dismiss with `Ctrl-e`
|`z=` |Normal |List numbered suggestions for the word under the cursor; pick one by number
|`zg` / `zw` |Normal |Add the word under the cursor to the dictionary as good / wrong
|`++[++s` / `++]++s` |Normal |Jump to the previous / next misspelling
|===

`Ctrl-x` is bound nowhere in this config and blink binds only `Ctrl-n`, `Ctrl-p`,
`Ctrl-y`, `Ctrl-e`, `Ctrl-k`, `Ctrl-f` and `Ctrl-b`, so `Ctrl-x s` reaches Vim's
own handler and coexists with the completion menu.

=== Command-line Completion

[cols=",",options="header",]
|===
|Mode |Sources
|`/` or `?` search |Buffer words
|`:` commands |File paths, then Ex commands
|===

The menu appears on its own at these prompts (`auto_show`), so you usually will not need
the trigger. The keys are the same as insert mode — `Ctrl-y` accepts, `Ctrl-n`/`Ctrl-p`
walk the list, `Ctrl-e` cancels, `Ctrl-k` shows documentation — and `Enter` executes the
command line as always. Completing a command is therefore `:Blin` `Ctrl-n` `Ctrl-y`.

`Ctrl-k` is bound here as well, because the command line uses the same keymap table, but in
practice it has nothing to show: command-line candidates carry only the short grey
description rendered inline in the menu, not the `detail` or `documentation` fields the
window renders. It is harmless — it will not disturb what you have typed — but do not
expect a documentation window at the `:` prompt.

TIP: Command-line *history* is on `Up` and `Down`, not `Ctrl-p`/`Ctrl-n` — and they are the
better keys for it, since they recall only entries matching what you have already typed.
`Ctrl-n`/`Ctrl-p` belong to the completion menu.

You may notice `Ctrl-p` recalling history on an *empty* command line. That is the `fallback`
entry doing its job: with no menu open there is nothing to select, so the key does whatever
Neovim natively does with it. `Ctrl-n` does not behave symmetrically, because it carries the
trigger role — `show` succeeds and opens the menu, so it never reaches the fallback. The
fallback rule is the same in both modes; only Neovim's native meaning differs (history on the
command line, keyword completion in insert mode).

NOTE: `Tab` does not select items in blink's menu here. blink's stock command-line preset
used it, but this configuration uses the shared keymap instead so that insert mode and the
command line cannot drift apart. `Tab` therefore falls back to Neovim's own wildmenu, which
is still perfectly usable — `wildmode=full` completes to the first full match and further
presses cycle through the rest. It is deliberately left alone rather than rebound, because
wildmenu `Tab` exists only on the command line: a habit built on it would fail in insert
mode, which is the exact drift this keymap sets out to remove. Use `Ctrl-n` if you want one
key that behaves the same in both places.

`:ConformInfo` does not exist until then.

== Treesitter Parsers (nvim-treesitter)

This config tracks nvim-treesitter's `main` branch. Parsers listed in
`lua/plugins/treesitter.lua` are installed at startup if missing, and
lazy.nvim runs `:TSUpdate` whenever it installs or updates nvim-treesitter. Parsers go to
`~/.local/share/nvim/site/parser/`.

[cols=",",options="header",]
|===
|Command |Action
|`:TSInstall \{lang} …` |Download, build and install one or more parsers, asynchronously. Skips parsers already installed. `\{lang}` may also be a tier: `stable`, `unstable` or `all`
|`:TSInstall! \{lang} …` |Reinstall even if already installed
|`:TSUpdate [\{lang} …]` |Update installed parsers to the revision nvim-treesitter pins; all installed parsers when no argument is given
|`:TSUninstall \{lang} …` |Delete the named parsers; `all` deletes every parser
|`:TSLog` |Show the messages from previous install, update and uninstall runs
|===

`\{lang}` is the parser name, not the filetype: `commonlisp` for Lisp,
`c_sharp` for C#, `janet_simple` for Janet. `Tab` completes it —
`:TSInstall` offers every available parser, `:TSUpdate` and `:TSUninstall`
only installed ones.

`:TSUninstall` of a parser in the startup list lasts only until the next
start, which installs it again. Remove it from the `ts.install({ … })` list
in `lua/plugins/treesitter.lua` as well.

Building a parser needs the `tree-sitter` CLI, a C compiler, `curl` and
`tar` — see xref:getting-started.adoc#tree-sitter-cli[tree-sitter CLI]. When
an install fails, `:TSLog` shows which step failed.

== Folding Commands (nvim-ufo)

Fold keys are listed in the xref:editor/keybindings.adoc[Keybindings]
cheatsheet. nvim-ufo computes the folds: LSP folding ranges first, then
treesitter where the language has a fold query, else indent. Markdown uses
treesitter then indent. AsciiDoc is left to vim-asciidoctor.

These commands have no keymaps and are mainly for diagnosing folds that are
missing or wrong:

[cols=",",options="header",]
|===
|Command |Action
|`:UfoInspect` |Show, for the current buffer, the fold status, main and fallback provider, the provider actually in use, the fold kinds present and the fold range under the cursor. Reports `Buffer N has not been attached.` if ufo is not managing the buffer
|`:UfoDisableFold` |Stop updating folds for the current buffer; the folds already there are left in place
|`:UfoEnableFold` |Resume computing folds for the current buffer and update them now
|`:UfoDetach` |Detach ufo from the current buffer, turning off all its features there
|`:UfoAttach` |Attach ufo to the current buffer again
|`:UfoDisable` |Turn ufo off for every buffer
|`:UfoEnable` |Turn ufo back on after `:UfoDisable`
|===

ufo loads on the first `BufReadPost`, so these commands exist once a file
has been opened.

_Configured in `lua/plugins/ufo.lua`._
