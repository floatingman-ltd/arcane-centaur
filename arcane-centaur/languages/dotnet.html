Quick Start

C#

  1. Open any .cs file — Roslyn attaches automatically.

  2. If the project has multiple .sln files, run :Roslyn target to pick the solution.

  3. Start the REPL with ,sl on any line, or open it explicitly via iron.nvim’s :IronRepl.

F#

  1. Verify prerequisites:

    dotnet --version
dotnet tool list -g | grep fsautocomplete

  2. Open a .fs source file — plugins and LSP attach automatically.

  3. Start the REPL with ,sl on any line.

REPL Commands (C# and F#)

iron.nvim loads with the first .cs or F# buffer; its commands exist from then on. [ft] defaults to the current buffer’s filetype — cs (csharprepl) or fsharp (dotnet fsi) — and <Tab> completes it.

Command Action

:IronRepl [ft]

Open the REPL in the bottom split; if it is already running, show or hide its window

:IronReplHere [ft]

Open the REPL in the current window instead of a split

:IronFocus [ft]

Move the cursor into the REPL window, starting the REPL if needed

:IronHide [ft]

Close the REPL window; the REPL keeps running

:IronRestart

Start a fresh REPL of the same filetype and wipe the old one, without asking

:IronSend {text}

Send text to the current filetype’s REPL

:IronSend! {ft} {text}

Send text to the ft REPL, starting it if needed

:IronWatch file

On every write of this buffer, send the whole file

:IronWatch mark

On every write of this buffer, resend the region last sent with ,sl / ,sc

:IronAttach {ft}

Make this buffer send to the ft REPL whatever its own filetype, e.g. :IronAttach fsharp in a scratch buffer

There is no command to stop :IronWatch; :lua require("iron.core").unwatch(0) removes the watch from the current buffer.

F# — Indentation

Pressing Enter after a line that opens a body — one ending in =, →, then, else, or a match arm — indents the new line one shiftwidth deeper. ==, >> and << work as reindent operators.

This comes from the editor, not from the language server. No language server supplies indentation; LSP has no indent-as-you-type concept. Indentation therefore keeps working with fsautocomplete absent, still starting, or unable to resolve options for a standalone .fsx.

The implementation is a vendored third-party file, indent/fsharp.vim, taken from Ionide-vim at a recorded commit. The plugin itself is deliberately not installed: only that one file is wanted, and the rest of the plugin duplicates configuration that already works here — it registers a second FsAutoComplete client, sets fdm=syntax in place of the LSP folds, ships a regex syntax file instead of treesitter, changes commentstring, and binds FSI keymaps that collide with iron.nvim.

One function in the vendored file differs from upstream: its comment and string detection used synID(), which needs a Vim :syntax file and so was inert under treesitter highlighting. Read the file’s header before editing or refreshing it.

Commenting is fixed in the same place and for the same reason. Neovim ships no ftplugin for F#, so commentstring was unset and <leader>-style native commenting (gcc, gc) failed with comment string is empty. F# buffers now use // %s, with comments set so XML doc comments (///) are recognised ahead of plain line comments and (* *) blocks are handled.

F# is the only language here that needs a hand-written indent script. nvim-treesitter ships no indents.scm for F#, and smartindent keys off {, } and cinwords, none of which F# uses.

F# — Formatting (fsautocomplete)

Format-on-save is enabled via conform.nvim using the fsautocomplete formatter, which in turn delegates to Fantomas.

Fantomas must be installed separately — dotnet tool install -g fantomas. fsautocomplete does not ship it, and without it a write does not merely skip formatting: the server raises an interactive prompt

No Fantomas install was found.:
1: Install locally
2: Install globally

which blocks every save of an F# buffer.

Format-on-save needs resolved project options, so it is unreliable on a standalone .fsx script. fsautocomplete resolves options per project; for a script outside any .fsproj that resolution intermittently cancels with

Error getting project options for <path> - A task was canceled.

after which Fantomas is never invoked and the buffer writes unformatted with nothing else in :messages to explain it. It is a race, so the same file may format one time and not the next.

Inside a project it is reliable. If a script must be formatted, <leader>f after the server has settled is more dependable than relying on the write.

Fantomas applies its own house style, not just indentation repair — it will collapse multi-line match arms and if/elif/else chains onto single lines where they fit, and normalise Rect (w, h) to Rect(w, h). Expect saved files to be restructured, not merely re-indented.

Manual trigger:

Keys Action

<leader>f

Format buffer or visual selection

Debugging (nvim-dap + netcoredbg)

Breakpoint debugging for C# and F# is provided by nvim-dap
nvim-dap-ui with the netcoredbg adapter, which easy-dotnet auto-registers with nvim-dap once both are loaded (there is no hand-written dap.adapters entry — a session therefore only starts from a .cs/.fsharp buffer, where easy-dotnet is loaded).

Prerequisites

netcoredbg is not a NuGet / dotnet tool package (there is no dotnet tool install -g netcoredbg). Download the prebuilt binary from the Samsung/netcoredbg releases and put it on your $PATH.

Linux / WSL2 (x64):

# Resolve the latest release tag, download the linux-amd64 build, and extract it
NCDBG_VER=$(curl -s https://api.github.com/repos/Samsung/netcoredbg/releases/latest \
  | grep '"tag_name"' | cut -d'"' -f4)
curl -L "https://github.com/Samsung/netcoredbg/releases/download/${NCDBG_VER}/netcoredbg-linux-amd64.tar.gz" \
  -o /tmp/netcoredbg.tar.gz
mkdir -p ~/.local/share/netcoredbg
tar -xzf /tmp/netcoredbg.tar.gz -C ~/.local/share/netcoredbg/

# Locate the binary — the archive unpacks into a nested netcoredbg/ directory
find ~/.local/share/netcoredbg -name netcoredbg -type f

# Add that directory to PATH (~/.zshenv), then reload
echo 'export PATH="$HOME/.local/share/netcoredbg/netcoredbg:$PATH"' >> ~/.zshenv
exec zsh

Verify it is on your $PATH:

netcoredbg --version

Release 3.2.0-1092 unpacks to ~/.local/share/netcoredbg/netcoredbg/netcoredbg. If find prints a different directory for a later release, put that directory on PATH instead.

Testing (easy-dotnet)

easy-dotnet.nvim provides a .NET test runner, project picker, and solution management using fzf-lua. It does NOT manage the Roslyn LSP — roslyn.nvim remains the sole C# language server.

easy-dotnet.nvim is a thin client over a separate EasyDotnet server tool, which powers all its features (debug, test, run, build). Install it once:

dotnet tool install -g EasyDotnet     # provides the `dotnet-easydotnet` executable
dotnet-easydotnet -v                  # verify (needs ~/.dotnet/tools on PATH)

Without it, every :Dotnet … action (and <F5> debug) errors 'dotnet-easydotnet' is not executable. Run :checkhealth easy-dotnet to confirm the server and the other dependencies (dap, fzf-lua, the c_sharp parser).

Test / Run / Build Keymaps (C# and F# buffers)

Keys Action

,tt

Run tests for selected project

,tr

Run selected project

,tb

Build selected project

Run/test output opens in a managed terminal that stays open on exit (we set managed_terminal.auto_hide = false; the default closes it the moment a run exits 0). Dismiss it with q.

easy-dotnet resolves the target project from Neovim’s current working directory (vim.fn.getcwd()), not the current buffer, and it caches one active project (shown in lualine). Open Neovim from the project’s directory (or :lcd %:p:h) so ,tr/,tt/,tb act on the project you mean.

F# projects need a solution file. easy-dotnet’s runnable-project discovery is C#-oriented, so a standalone .fsproj isn’t found ("No runnable projects found") even though dotnet run works — add a .sln (or .slnx) alongside it. C# .csproj projects are discovered without one.

Easy-Dotnet Commands

Every easy-dotnet action is a :Dotnet subcommand; :Dotnet <Tab> completes them. They are available once a .cs or .fs buffer has loaded the plugin.

Picking a project. The plain form of a command opens a picker every time. The default form asks once, remembers the choice, and reuses it; :Dotnet reset forgets it.

Arguments. run, debug, watch, build, test and restore accept trailing arguments. release or debug as the first argument is shorthand for -c Release / -c Debug, e.g. :Dotnet build release. For build, test and restore the rest go to the dotnet command line; for run, debug and watch they are passed through to the run.

Typical Workflow

 +------------------------------------------------------+
 |  Neovim                                              |
 |  +--------------------------+---------------------+  |
 |  |  Program.cs / hello.fs   |  REPL               |  |
 |  |                          |                     |  |
 |  |  var x = 42;             |  > var x = 42;      |  |

Troubleshooting

Roslyn does not attach

Check that Microsoft.CodeAnalysis.LanguageServer is on your $PATH:

which Microsoft.CodeAnalysis.LanguageServer

If not found, re-run the install steps in Setup.

fsautocomplete does not attach

Check that it’s installed:

dotnet tool list -g | grep fsautocomplete

Run :lua =vim.lsp.get_clients({bufnr=0}) inside Neovim to check whether the server is attached to the current buffer. To open the LSP log:

:lua vim.cmd('e ' .. vim.lsp.get_log_path())

:checkhealth lsp gives a broader overview of LSP status.

REPL does not open

Check that the REPL backend binary is on your $PATH:

which csharprepl      # C#
dotnet fsi --version  # F#

Installing the Roslyn Language Server

The Roslyn LSP is the official Microsoft C# language server used in VS Code’s C# Dev Kit. It is not installed via dotnet tool install, and it is not on the public nuget.org feed. It is published to Microsoft’s Azure DevOps vs-impl feed, and every release is a prerelease (there is no stable 5.x — the newest is 5.4.0-2.26179.14 at the time of writing; there is no 5.5/5.6).

Linux / WSL2 (x64):

# 1. Resolve the newest version from the Azure DevOps vs-impl feed
PKG=microsoft.codeanalysis.languageserver.linux-x64
FEED="https://pkgs.dev.azure.com/azure-public/vside/_packaging/vs-impl/nuget/v3/flat2/${PKG}"
VERSION=$(curl -s "${FEED}/index.json" | tr ',' '\n' | grep -oE '[0-9][0-9.]+-[0-9.]+' | sort -V | tail -1)
echo "Installing Roslyn LSP ${VERSION}"

# 2. Download the linux-x64 package (self-contained native binary)
mkdir -p ~/.local/share/roslyn
curl -L "${FEED}/${VERSION}/${PKG}.${VERSION}.nupkg" -o /tmp/roslyn.nupkg

# 3. Extract into the install directory and make executable (needs `unzip`)
unzip -o -q /tmp/roslyn.nupkg -d ~/.local/share/roslyn
chmod +x ~/.local/share/roslyn/content/LanguageServer/linux-x64/Microsoft.CodeAnalysis.LanguageServer

# 4. Add to PATH (~/.zshenv — see Installing .NET SDK for why), then reload
echo 'export PATH="$HOME/.local/share/roslyn/content/LanguageServer/linux-x64:$PATH"' >> ~/.zshenv
exec zsh

# 5. Verify
Microsoft.CodeAnalysis.LanguageServer --version

Browse all versions at ${FEED}/index.json. The nuget.org package of the same name carries only a single stale prerelease — do not use it. To pin a specific version instead of auto-resolving the newest, set VERSION= manually (e.g. VERSION=5.4.0-2.26179.14).

Installing .NET SDK

Install every SDK you need — here .NET 8 and .NET 10 — side by side into ~/.dotnet with Microsoft’s dotnet-install.sh. One dotnet then serves both: it builds with the newest SDK unless a repo’s global.json pins an older one, and runs each project on the runtime matching its <TargetFramework>.

Linux / WSL2 (Ubuntu):

curl -sSL https://dot.net/v1/dotnet-install.sh -o /tmp/dotnet-install.sh
bash /tmp/dotnet-install.sh --channel 10.0 --install-dir ~/.dotnet
bash /tmp/dotnet-install.sh --channel 8.0 --install-dir ~/.dotnet

Re-running either --channel line later installs the latest patch next to the existing one.

Then put the install on $PATH, together with ~/.dotnet/tools where dotnet tool install -g puts its commands. Under zsh, use ~/.zshenv: zsh reads it for every shell, including ones that do not descend from your interactive terminal (an ssh host cmd, wsl.exe -e, a scheduled job), whereas ~/.zshrc is read only by interactive shells. typeset -U drops duplicate $PATH entries when shells nest.

printf '%s\n' 'typeset -U path PATH' 'export DOTNET_ROOT="$HOME/.dotnet"' 'export PATH="$HOME/.dotnet:$HOME/.dotnet/tools:$PATH"' >> ~/.zshenv
exec zsh

Verify, from a fresh non-interactive shell:

zsh -c 'echo $DOTNET_ROOT; command -v dotnet'   # ~/.dotnet and ~/.dotnet/dotnet
dotnet --list-sdks                              # an 8.0.x and a 10.0.x line
dotnet --list-runtimes                          # Microsoft.NETCore.App 8.0.x and 10.0.x

Do not mix this with Ubuntu’s apt packages. apt (dotnet-sdk-8.0 and friends) installs to /usr/lib/dotnet and carries one version per package source, so it cannot supply 8 and 10 together on Ubuntu 24.04. It also writes /etc/dotnet/install_location, which points at /usr/lib/dotnet; a global tool started without DOTNET_ROOT set looks there, finds no .NET 10 runtime, and fails even though dotnet --list-runtimes in your shell lists one. Check for a leftover apt install:

dpkg -l | grep -i dotnet                                   # should print nothing
which -a dotnet; cat /etc/dotnet/install_location* 2>/dev/null

If dpkg lists packages, remove them (read apt’s removal list before confirming):

sudo apt remove dotnet-sdk-8.0 dotnet-runtime-8.0 dotnet-host-8.0 dotnet-hostfxr-8.0 dotnet-apphost-pack-8.0 dotnet-targeting-pack-8.0 dotnet-templates-8.0

If you keep them, DOTNET_ROOT and the ~/.dotnet entry ahead of /usr/bin on $PATH are what keep the apt copy out of the way.

Running or debugging a project needs the runtime that matches its <TargetFramework>, not just any SDK. The 10.0 SDK builds a net8.0 project, but running it needs Microsoft.NETCore.App 8.0.x, which the --channel 8.0 install provides. Microsoft’s support for .NET 8 ended on 2026-11-10; .NET 10 is the current LTS. The editor toolchain here (roslyn.nvim, fsautocomplete, csharprepl, easy-dotnet, netcoredbg) works with either.

Verifying the toolchain

Once the SDKs, global tools, Roslyn, and netcoredbg are installed, build and run one project per target framework:

dotnet new console -f net8.0 -o /tmp/t8 && dotnet run --project /tmp/t8      # Hello, World!
dotnet new console -f net10.0 -o /tmp/t10 && dotnet run --project /tmp/t10   # Hello, World!
dotnet new console -lang F# -o /tmp/f10

Then, in Neovim:

  1. cd /tmp/t10 && nvim Program.cs, wait for the project to load, and run :checkhealth vim.lsp — it lists an active roslyn client.

  2. K on Console opens hover documentation.

  3. Indent the Console.WriteLine line wrongly and :w — CSharpier restores it.

  4. <F9> on that line, then <F5> — the debugger stops there and dap-ui opens. <S-F5> ends the session.

  5. cd /tmp/f10 && nvim Program.fs — :checkhealth vim.lsp lists fsautocomplete, and :w saves without a "No Fantomas install was found" prompt.

Clean up with rm -rf /tmp/t8 /tmp/t10 /tmp/f10.
